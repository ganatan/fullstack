# Benchmark Rust vs Python avec oha

`oha` est un outil de test de charge HTTP écrit en Rust, basé sur Tokio. Il permet d'envoyer un grand nombre de requêtes concurrentes vers une API et d'en mesurer les performances.

Endpoint testé :

```text
GET http://localhost:3000/persons
```

L'objectif est de comparer deux backends avec exactement le même scénario :

```text
Rust
Python
```

---

## 1. Installer oha

`oha` peut être installé directement avec Cargo.

```bash
cargo install oha
```

Sous Windows, il est également disponible avec `winget`.

```powershell
winget install hatoo.oha
```

---

## 2. Vérifier l'installation

```bash
oha --version
```

Afficher les options disponibles :

```bash
oha --help
```

---

## 3. Vérifier l'API

Avant le benchmark, démarrer le backend puis vérifier :

```text
http://localhost:3000/persons
```

La réponse doit être retournée correctement.

---

## 4. Principe du benchmark

Avec JMeter, nous utilisions des utilisateurs virtuels.

Avec `oha`, le paramètre principal est le nombre de connexions HTTP concurrentes :

```text
-c 100
```

`oha` documente `-c` comme le nombre de connexions exécutées simultanément.

Le benchmark utilisera :

```text
100 connexions concurrentes
60 secondes
requêtes envoyées en continu
aucune limitation de débit
KeepAlive activé
```

---

## 5. Configuration du benchmark

Commande de base :

```powershell
oha -c 100 -z 60s http://localhost:3000/persons
```

Les paramètres sont :

```text
-c 100
```

100 connexions HTTP sont utilisées simultanément.

```text
-z 60s
```

Le générateur envoie des requêtes pendant 60 secondes.

---

## 6. Correspondance avec JMeter

| JMeter              | oha                 | Explication                                    |
| ------------------- | ------------------- | ---------------------------------------------- |
| Users / Threads     | `-c 100`            | 100 connexions concurrentes                    |
| Loop Count Infinite | implicite avec `-z` | Les requêtes continuent pendant toute la durée |
| Duration 60 s       | `-z 60s`            | Charge pendant 60 secondes                     |
| Timer aucun         | aucun `-q`          | Pas de limitation volontaire du débit          |
| KeepAlive activé    | activé par défaut   | Les connexions TCP peuvent être réutilisées    |
| Endpoint            | URL                 | `http://localhost:3000/persons`                |

`oha` propose une option `--disable-keepalive` pour désactiver explicitement la réutilisation des connexions ; en ne l'utilisant pas, le KeepAlive reste actif.

---

## 7. Ramp-up

Le scénario JMeter utilisait :

```text
Ramp-up : 20 secondes
```

La CLI actuelle de `oha` documente la concurrence avec `-c` et la durée avec `-z`, mais ne fournit pas de paramètre équivalent direct au `Ramp-up` progressif de JMeter.

Le benchmark `oha` sera donc :

```text
0 seconde
    ↓
100 connexions concurrentes
    ↓
GET /persons en continu
    ↓
60 secondes
```

Il s'agit donc d'une charge immédiate de 100 connexions.

Les résultats `oha` doivent être comparés entre eux et non directement mélangés avec les résultats JMeter.

---

## 8. Ne pas limiter le débit

Ne pas utiliser :

```text
-q
```

L'option `-q` permet de limiter le nombre global de requêtes par seconde.

Pour notre benchmark, nous voulons au contraire laisser le backend répondre aussi rapidement que possible.

Le principe est :

```text
requête
    ↓
réponse
    ↓
nouvelle requête immédiatement
    ↓
réponse
    ↓
...
```

---

## 9. Attendre les requêtes en cours

Lorsque la durée `-z` est atteinte en HTTP/1, `oha` peut interrompre les requêtes encore en cours.

L'option :

```text
-w
```

permet d'attendre leur terminaison.

Nous utiliserons donc :

```powershell
oha -c 100 -z 60s -w http://localhost:3000/persons
```

Les nouvelles requêtes sont envoyées pendant 60 secondes, puis les dernières requêtes déjà en cours peuvent terminer proprement.

---

## 10. Warm-up

Avant les mesures officielles, effectuer un test de chauffe de :

```text
30 secondes
```

Commande :

```powershell
oha -c 100 -z 30s -w http://localhost:3000/persons
```

Les résultats du warm-up ne sont pas conservés.

Le but est simplement de préparer :

```text
backend
pool PostgreSQL
connexions HTTP
KeepAlive
```

## 12. Benchmark Python

Démarrer le backend Python :

```powershell
python -m src.main
```

Puis exécuter exactement le même benchmark :

```powershell
oha -c 100 -z 60s -w http://localhost:3000/persons
```

Seul le backend exécuté change.

La commande `oha` reste strictement identique.

---

## 13. Benchmark sans interface temps réel

Pour les mesures officielles, utiliser :

```text
--no-tui
```

`oha` indique qu'un chemin d'exécution plus rapide est utilisé avec `--no-tui` lorsque la limitation QPS et le mode burst ne sont pas activés.

Commande recommandée :

```powershell
oha -c 100 -z 60s -w --no-tui http://localhost:3000/persons
```

C'est cette commande qui doit être utilisée pour les benchmarks comparatifs.

---

## 14. Enregistrer les résultats

`oha` permet d'enregistrer le résultat avec :

```text
-o
```

et de choisir le format avec :

```text
--output-format
```

Les formats documentés comprennent notamment `text`, `json`, `csv` et `quiet`.

Créer le dossier :

```text
benchmarks
```

Pour Rust :

```powershell
oha -c 100 -z 60s -w --no-tui --output-format json -o "benchmarks\rust.json" http://localhost:3000/persons
```

Pour Python :

```powershell
oha -c 100 -z 60s -w --no-tui --output-format json -o "benchmarks\python.json" http://localhost:3000/persons
```

---

## 15. Nombre de benchmarks

Pour chaque backend :

```text
Warm-up : 30 secondes

Run 1 : 60 secondes
Run 2 : 60 secondes
Run 3 : 60 secondes
```

Pour conserver séparément les trois résultats Rust :

```powershell
oha -c 100 -z 60s -w --no-tui --output-format json -o "benchmarks\rust-run-1.json" http://localhost:3000/persons
```

```powershell
oha -c 100 -z 60s -w --no-tui --output-format json -o "benchmarks\rust-run-2.json" http://localhost:3000/persons
```

```powershell
oha -c 100 -z 60s -w --no-tui --output-format json -o "benchmarks\rust-run-3.json" http://localhost:3000/persons
```

Puis la même chose pour Python :

```powershell
oha -c 100 -z 60s -w --no-tui --output-format json -o "benchmarks\python-run-1.json" http://localhost:3000/persons
```

```powershell
oha -c 100 -z 60s -w --no-tui --output-format json -o "benchmarks\python-run-2.json" http://localhost:3000/persons
```

```powershell
oha -c 100 -z 60s -w --no-tui --output-format json -o "benchmarks\python-run-3.json" http://localhost:3000/persons
```

Utiliser ensuite la valeur médiane des trois runs pour la comparaison.

## 16. Afficher les résultats directement

Sans fichier de sortie :

```powershell
oha -c 100 -z 60s -w --no-tui http://localhost:3000/persons
```

`oha` affiche par défaut un résumé textuel du benchmark.

Le résultat contient notamment des informations comme :

```text
Success rate
Total
Slowest
Fastest
Average
Requests/sec
Response time distribution
Status code distribution
```

---

## 17. Résultats importants

### Success rate

Pourcentage de requêtes réussies.

Objectif :

```text
100 %
```

---

### Requests/sec

Nombre de requêtes traitées par seconde.

```text
plus élevé = meilleur
```

C'est la mesure principale pour comparer la capacité de traitement des deux backends.

---

### Average

Temps moyen nécessaire pour répondre à une requête.

```text
plus bas = meilleur
```

---

### Fastest

Réponse la plus rapide du benchmark.

```text
plus bas = meilleur
```

---

### Slowest

Réponse la plus lente.

```text
plus bas = meilleur
```

---

### Response time distribution

`oha` fournit également plusieurs percentiles de temps de réponse, par exemple :

```text
50 %
90 %
95 %
99 %
```

Ils permettent de voir comment se comportent les requêtes les plus lentes.

---

### Status code distribution

Permet de vérifier les codes HTTP obtenus.

Résultat attendu :

```text
200
```

pour toutes les requêtes.

## 20. JMeter vs oha

Les deux outils ne modélisent pas exactement la charge de la même manière.

### JMeter

```text
100 utilisateurs virtuels
Ramp-up possible
boucles
Thread Group
Listeners
```

### oha

```text
100 connexions concurrentes
durée fixe
charge immédiate
outil CLI léger
résultats directement dans le terminal
```

Le benchmark `oha` permet ainsi d'obtenir un second point de comparaison simple entre les backends Rust et Python.

La commande de référence reste :

```powershell
oha -c 100 -z 60s -w --no-tui http://localhost:3000/persons
```
