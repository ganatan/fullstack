# Dépendances

Ajouter Hibernate ORM avec Panache :

```xml
<dependency>
  <groupId>io.quarkus</groupId>
  <artifactId>quarkus-hibernate-orm-panache</artifactId>
</dependency>
```

Conserver le driver PostgreSQL utilisé à l'étape précédente :

```xml
<dependency>
  <groupId>io.quarkus</groupId>
  <artifactId>quarkus-jdbc-postgresql</artifactId>
</dependency>
```

On possède donc :

```text
quarkus-hibernate-orm-panache
        ↓
Hibernate ORM
        ↓
JPA

quarkus-jdbc-postgresql
        ↓
JDBC PostgreSQL
        ↓
Agroal
```

La dépendance PostgreSQL ne disparaît pas.

Hibernate utilise toujours JDBC en interne.

# schema-management.strategy

La propriété :

```properties
quarkus.hibernate-orm.schema-management.strategy=validate
```

demande à Hibernate de vérifier que les entités correspondent au schéma PostgreSQL existant.

Hibernate :

```text
ne crée pas la table
ne supprime pas la table
ne modifie pas la table
```

Il vérifie uniquement la cohérence :

```text
@Entity
   ↓
Hibernate
   ↓
validation
   ↓
table PostgreSQL
```

La table reste donc créée manuellement.

  }

      String firstName,

      int cityId

    this.firstName =
        firstName;

    this.lastName =
        lastName;

    this.cityId =
        cityId;

  }

  public Person(
      Integer id,
      String firstName,
      String lastName,

  ) {

    this.id =
        id;

    this.firstName =
        firstName;

    this.lastName =
        lastName;

    this.cityId =
        cityId;

  }

  public Integer getId() {

    return id;

  }

  public String getFirstName() {

    return firstName;

  }

  public void setFirstName(

    this.firstName =

# PersonRepository

Avec Spring Data JPA :

```java
public interface PersonRepository
    extends JpaRepository<Person, Integer>
```

Avec Quarkus Panache :

```java
@ApplicationScoped
public class PersonRepository
    implements PanacheRepositoryBase<Person, Integer>
```

Le repository reste donc une vraie couche applicative injectable.

---

# Pourquoi PanacheRepositoryBase ?

Il existe :

```java
PanacheRepository<Person>
```

mais ce repository utilise le type d'identifiant standard :

```text
Long
```

Notre entité utilise :

```java
Integer id
```

On utilise donc :

```java
PanacheRepositoryBase<Person, Integer>
```

Cela permet de conserver exactement notre modèle :

```text
Person
ID = Integer
```

@ApplicationScoped
public class PersonRepository

    implements PanacheRepositoryBase<
        Person,

    return find(

# Modification

La modification est particulièrement intéressante avec Hibernate.

On récupère :

```java
Person person = personRepository
    .findByIdOptional(id)
    .orElseThrow();
```

Puis :

```java
person.setFirstName(
    firstName
);

person.setLastName(
    lastName
);

person.setCityId(
    cityId
);
```

Si `Person` est une entité gérée dans une transaction, Hibernate détecte automatiquement ses modifications.

Il n'est donc pas nécessaire d'appeler :

```text
save()
```

ni :

```text
update()
```

Flux :

```text
Person chargée
    ↓
entité gérée par Hibernate
    ↓
setFirstName()
setLastName()
setCityId()
    ↓
fin de transaction
    ↓
dirty checking
    ↓
UPDATE SQL
    ↓
PostgreSQL
```

## Code

```java
package com.ganatan.starter.api.person;

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.transaction.Transactional;

import java.util.List;
import java.util.Optional;

@ApplicationScoped
public class PersonService {

  private final PersonRepository personRepository;

  public PersonService(
      PersonRepository personRepository
  ) {

    this.personRepository =
        personRepository;

  }

  public List<Person> getAllPersons() {

    return personRepository
        .findAllByOrderByIdAsc();

  }

  public Optional<Person> getPersonById(
      int id
  ) {

    return personRepository
        .findByIdOptional(id);

  }

  @Transactional
  public Person createPerson(
      String firstName,
      String lastName,
      int cityId
  ) {

    Person person = new Person(
        firstName,
        lastName,
        cityId
    );

    personRepository.persist(
        person
    );

    return person;

  }

  @Transactional
  public Optional<Person> updatePerson(
      int id,
      String firstName,
      String lastName,
      int cityId
  ) {

    Optional<Person> existing =
        personRepository
            .findByIdOptional(id);

    if (existing.isEmpty()) {

      return Optional.empty();

    }

    Person person =
        existing.get();

    person.setFirstName(
        firstName
    );

    person.setLastName(
        lastName
    );

    person.setCityId(
        cityId
    );

    return Optional.of(
        person
    );

  }

  @Transactional
  public boolean deletePerson(
      int id
  ) {

    return personRepository
        .deleteById(id);

  }

}
```

# Modification et Dirty Checking

Contrairement à la version Spring Data JPA :

```java
personRepository.save(
    person
);
```

n'existe pas ici.

Une entité récupérée avec :

```java
personRepository.findByIdOptional(id)
```

pendant une transaction est gérée par Hibernate.

Après :

```java
person.setLastName(
    lastName
);
```

Hibernate détecte la modification.

À la fin de la transaction :

```text
Hibernate
    ↓
compare l'état de l'entité
    ↓
détecte la modification
    ↓
génère UPDATE
```

Ce mécanisme est appelé :

```text
Dirty Checking
```

# Point architectural

La séparation reste entièrement intacte :

```text
Controller
    ↓
Service
    ↓
Repository
```

Seule la technologie située derrière le repository évolue.

Avant :

```text
PersonRepository
    ↓
JDBC manuel
```

Maintenant :

```text
PersonRepository
    ↓
Panache
    ↓
Hibernate ORM
```

Le changement supplémentaire concerne :

```text
Person
```

qui devient :

```text
@Entity
```

Cela introduit volontairement un couplage :

```text
Person
    ↓
Jakarta Persistence
```

Une architecture encore plus découplée pourrait séparer :

```text
Person
```

et :

```text
PersonEntity
```

mais cette séparation n'est pas nécessaire pour cette première architecture Hibernate.
